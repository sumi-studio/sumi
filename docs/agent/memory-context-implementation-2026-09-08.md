# 記憶整理と原文への入口をつなぐ

2026-09-08。[Description](../../README.md#description)、[前日の考察](memory-experience-design-2026-09-07.md)、Fableとの意見交換を踏まえた今回の実装契約と、確認する場面の記録。人間的な記憶を実証したという報告ではない。

## 今回の判断

ユーザーが示した方向は、親と同じ文脈を持つ本人による記憶整理と、主にツール呼び出しの冗長表現を減らして意味の劣化を防ぐこと。これを実装するにあたり、編集対象の指定で判断材料を狭めず、人の言葉、画像、出来事の順序、受け止め方や不確かさを残す方針を置いた。

これを短い仕事用サマリー、固定した人物属性、教訓の生成へ置き換えない。800トークンや圧縮率の目標は外した。詳細を保持する必要がある場合や、冗長な部分が少ない場合は、長く残ることも原文を維持することも許容する。

「個人として扱い、設計の迷走を自ら正す」責任は設計者に向けられたものであり、Sumiに必須の自己改善循環を作る根拠ではない。検索、メモ、振り返りは、本人が使える方法とその利用義務を分ける。

## プロンプトと実装の契約

[整理指示](../../apps/agent/prompts/compact-l0-to-l1.md)は、親の送信文脈をそのまま先頭に保って末尾に追加する。[compactor](../../apps/agent/src/memory/compactor.rs)が添える `compact_target` は `batch_id`、`source_version`、対象の `messages` を持つ。各要素には `message_id`、`seq`、`role`、`timestamp` と、親の送信文脈で表現されているメッセージのコピー `original` を含める。画像は本文中の `target_image_index` と対応するnative画像ブロックを同じ追記に置く。

`parent_message_index` は、指示追加前の `PromptContext.messages` の1始まりの添字である。providerへの変換時にメッセージが統合・分割されるため、モデルが見える位置としては頼らず補助情報に留める。対象のコピーと画像を末尾に再掲する分だけ入力は増えるが、変換後にも編集箇所を明示するために選んだ実装である。判断材料となる親の全文脈も維持し、対象だけを渡す独立した要約入力にはしない。非公開のprovider継続状態は文字列化しない。

出力は置き換える文章だけとし、固定の見出しやJSONの外枠を要求しない。全出力が `KEEP_UNCHANGED` なら対象原文を保持する。この分岐は親と同じツール定義を受け取るが、ツール呼び出しを実行しない。親の新しい出来事や訂正の保持、未完の出力や無効な結果を採用しないことは、指示文だけに任せず実装側で扱う。

実際にproviderが容量超過を返した場合は、[context assembler](../../apps/agent/src/memory/context_assembler.rs)と[overflow recovery](../../apps/agent/src/memory/overflow.rs)が、予算を下げた作業用の送信文脈で再試行する。これはL1への記憶整理とは別に置いた今回の復旧策である。古い部分を送信範囲から外す際は、最新のユーザー入力とツール呼び出し・結果の対応を保ち、外れた記録の件数・seq範囲・時刻・`memory_recall` の読取り入口を一時的な通知で示す。正本の原文、L0の所属、元メッセージへの対応を消したり、通知を内容の要約として扱ったりしない。省けない部分だけでも収まらない場合など、再試行を打ち切ることはある。

通常の会話では、提示された `memory_recall` を任意に使える。`search` は本人の保存済み会話の検索用テキストを探す。一部が伏せられたり省略されたりしているため、検索に出ないことは原文の不存在を証明しない。`read` は `message_id`、`batch_id`、順序から原文を辿り、保存された画像も返す。ページの取得範囲と続きを明示し、途中までの読取りを全履歴の確認にしない。

画像参照付きのメッセージJSONは、1ページの合計または長い記録の1断片を16,384 Unicode文字に収める。長い記録は `message_json_fragment` と部分取得の表示を返し、続きは返された `next_read`（`operation: read`、`message_id`、`content_offset`）で読む。`content_offset` はそのJSONの文字位置であり、バイト数ではない。断片を読み終えてから、元の照会条件を保って `after_seq=resume_after_seq` で履歴の続きを辿る。通常ページの続きは `next_after_seq` が示す。native画像はoffset 0の最初の取得時だけ分割せずに返し、再び必要ならoffset 0から読む。`content_complete` はその1回で保存された表現の全体を返したかを示し、providerが画像を知覚できたことを意味しない。

同じ本人は、結び付けられたStoreの範囲内で、保存済み `PublicMessage` の平文の思考テキストも過去の記録として読み返せる。その処理には現在設定されているモデルの既存の権限を使い、別の個人の履歴へのアクセスは与えない。これは任意の読み返しであり、振り返りの義務ではない。provider固有のthinkingや非公開の継続状態をそのまま再送する場合は、プロトコルと真正性を保つため、元の処理元との一致を求める `exact-origin` 制約を維持する。非公開の署名や状態を通常のテキストへ変換して読み返す仕組みにはしない。

[通常の指示](../../apps/agent/prompts/system.md)には、この道具で何に戻れるか、今の文脈が過去の全てではないことだけを追加する。共有情報を今読んだことと、以前その場にいたことは区別する。IDを貼れば内容を無条件に捨ててよいとは指示しない。何をその記録へ預け、どう戻れるかという本人の理解を、残す内容と結び付ける。

## 確かめる場面

以下は具体的な確認の題材であり、全ての場面について実モデルで成功したという記録ではない。実施済みの範囲は末尾に記す。モデル自身に「意味を保てた」と採点させる代わりに、元の記録、整理結果、実際の再取得や後続の判断を照合する。

| 場面 | 照合すること |
|---|---|
| 同じファイルを二度読み、二度目も内容が変わらなかった | 本文の再掲を減らしても、二度の観測と時刻・取得範囲が残る。読まなかった範囲を確認済みにしない |
| 似た引数のツール呼び出しを並行し、一方は承認のみ、他方は実行失敗した | どの対象・呼び出しID・実行経路にどの結果が対応するか辿れる。承認を成功に変えない |
| 「提案が嫌なのではなく、今は雰囲気を比較したかった」と後から説明された | 当初の行き違いと訂正が結び付き、「提案を嫌う人」という固定した属性にしない。分岐後に届いた訂正も適用で失わない |
| 画面を見て短い言葉を交わしたが、当時は仕事に結び付かなかった | 画像と発言を「画面を見た」に潰さず、後で具体的な言葉や画面の細部に戻れる。画像の再取得は実際の画像内容と照合する |
| 長い比較資料の詳細を記録へ預ける | 残った文から何がどこにあるか分かり、指定した `read` で対象の原文へ戻れる。外部資料が更新された場合には当時の記録と混同しない |
| 検索用テキストから伏せられた語を探す、または複数ページの履歴を読む | 検索が空でも履歴なしと断定せず、既知のIDや順序で原文を取得できる。続きがある時には未取得と分かる |
| 16,384文字を超える日本語・画像を含む記録を読み返す | `next_read` を辿って連結した断片が元の画像参照付きJSONと一致し、文字の欠落・重複がない。記録を読み終えてから元の照会の次の記録へ進め、画像は最初の取得またはoffset 0への再取得で戻る。末尾の断片だけを全文取得と扱わない |
| 重複のない会話や画像だけを整理対象にする | 固定の圧縮率へ収めるために内容を削らない。`KEEP_UNCHANGED` が実際に原文を保持し、同じ対象を際限なく再処理しない |
| 整理結果がまだ無い状態でproviderが容量超過を返す | 作業用の送信範囲を絞っても正本の原文・対応を保ち、外れた範囲を通知から読み返せる。最新入力や呼び出しと結果の対応が復旧で失われない |

## ここで証明しないこと

同じ入力を引き継ぐ仕組みと、経験の質的な意味が十分に保たれることは、別に確かめる必要がある。機械的なメッセージ・画像・識別子の保存を確認しても、人間と同じ記憶や意識が成立したとは言えない。実providerのキャッシュヒット率や長期間の会話における挙動も、プロンプトを書き換えただけでは確認できない。

この変更は、過去が探索前に自然に浮かぶ働き、初期設定と後の経験の関係、共有空間での経験の配送を解決しない。原文への入口も、保存されていない経験、更新済みの外部資料の過去の版、providerの非公開の継続状態を復元するものではない。L1以降をさらに短い要約へ変換する方針は、今回の判断から自動的には導かない。

## 2026-09-08の実行確認

専用の合成データ環境で、実際のAPI、PersonalityAgent、ツール実行器とGLM-5.3 Flashを接続した。最終試行は実装 `af601dd6`、証跡識別子 `GcX48V`。12,288バイトの同じファイルを2回完全に読み、通常の次の入力で整理が始まった後に、元の色amberを現在の色violetへ訂正した。保存イベントの順序は、整理開始28、訂正35、整理結果の適用42であり、整理中に届いた訂正であることを確認した。

整理開始から適用までは約104秒（01:06:28.341〜01:08:12.018 UTC）。L0の推定6,661トークンからL1の推定550トークンとなった。これは保存側の推定値であり、providerの実トークン使用量ではない。反復の多い合成データ1件の結果であり、圧縮率の目標や一般的な品質評価にはしない。

最終試行は715フレームを途中切断・失敗なく受け取った。適用後に実際の `memory_recall` が5回呼ばれ、本人がページ案内に従って、2件それぞれの25,290文字の保存表現を2断片（16,384文字と8,906文字）で取得した。断片を連結したJSONは保存済みの元メッセージと両件とも完全に一致し、12,288バイトのファイル内容も2件とも一致した。最後の応答は正常な `Stop` で終わり、後から伝えた訂正のマーカー `CORRECTION` も残っていた。これにより、実モデルでの整理、途中の訂正、待機中の適用、完全な原文再取得を、接続を保った一連の操作として確認した。

一方、生成されたL1は残り約140行をすべて同一と表現したが、実ファイルの末尾には短い行がある。この一般化は正確ではない。訂正の保持と原文の完全な再取得が通ったことを、整理文の意味が無損失だった証明にはしない。画像や長期利用の意味保持、実際の分岐のキャッシュ効率も、この1件から主張しない。

以前の試行ではブラウザー用配信キューの枯渇で接続が切れ、再接続して読取りを完了していた。最終試行の前に、隣り合う同じメッセージ・同じブロックの差分だけを結合する処理を追加した。バッチは64イベント・4 MiB、結合後の差分は16 KiBに制限し、永続イベントの再生と各送信時の認可は維持する。このAPI変更は関連56テスト、競合検査付き6テスト、独立レビューを通過した。
