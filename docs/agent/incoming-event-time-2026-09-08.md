# 入力を受け取った時刻と、その間隔

2026-09-08。ユーザーの指定は、ユーザーメッセージや外部イベントを受け取ったとき、その先頭または末尾に時刻と経過時間を添えること。[圧縮の実測](memory-temporal-probe-2026-09-08.md)では、通常の会話で見えていなかったUTC時刻が圧縮対象に現れ、モデルが本文の「朝9時」との間に根拠のない時間差を見いだす例があった。

## 時間情報の意味

今回の時刻は、Sumiの永続化された入力受付がメッセージを受け取った時刻。人が端末で書いた時刻や、本文で話している出来事が起きた時刻とは区別する。ユーザーのタイムゾーン設定はまだないため、表示するのは明示的なUTCであり、言語やサーバーの地域から現地時刻を推測しない。

前の入力については、その受信時刻とコマンドの順序を一緒に保持する。両受信時刻の差をモデルへ示すので、どこから測った間隔なのかが分かる。現在の実装対象はユーザー入力同士であり、Abortや承認回答をその間に挟んでも基準を更新しない。ツール結果をこの基準に含めるかは別の判断である。まだ存在しない一般的な外部イベントの受付経路を、この変更だけで実装済みとは扱わない。

最初の入力には、存在しない前回からの経過時間を作らない。差はUTCの時計の読みの差であり、単調増加時計で測った実時間とは同一視しない。時計の読みが戻った場合は、前回より時計が前に戻ったと明示する。

## 固定する場所と見せる場所

受信時刻と前の受信イベントは、永続化された受付時に一度だけ確定する。同じ入力の再配信、再起動後の復元、ステアリングによる取り込みでも、この値を引き継ぐ。過去のメッセージが圧縮され、現在見える直前のメッセージが変わっても、間隔を計算し直す基準にはしない。

原文の `content` に時間情報を書き込まず、`UserMessage` の独立した `incoming_timing` として保持する。現在の受信時刻は既存の `timestamp`、前回は `previous_receipt` の `command_seq` と `received_at`。初回は `previous_receipt: null`。通常の入力ではない内部指示には、この情報を作らない。

Chat Completions、Responses、Anthropicの各送信経路は、共通の整形処理で受信情報を本文の先頭に付ける。圧縮分岐はその親の文脈をそのまま引き継ぐ。毎回変わる「現在時刻」をsystemの先頭へ加えたり、圧縮のときだけ古い時刻を更新したりはしない。追加分は文脈の量の見積もりにも含める。

例えば、前の入力から受信時計で90秒後なら、モデルには次のように見える。接頭辞と本文は別のテキストブロックであり、下記は表示を一つに並べた例。

```text
[Received 2026-09-08 03:01:30 UTC; 1 minute 30 seconds since the previous incoming message]
さっきの続きだけど、別の案も見たい。
```

保存する時刻の精度と、モデルが読む表現は分ける。接頭辞の受信時刻は秒まで、間隔は秒・分・時間・日を用いて最大2単位で表す。丸めた場合は `approximately`、1秒未満なら `less than a second` とする。内部のコマンド番号や小数のmsを読ませない。

公開イベントの契約にはこの任意の情報を明記するが、ブラウザから送るコマンドの入力項目は増やさない。画面は元の本文を表示し、受信情報の接頭辞をチャット本文には表示しない。

## 検証

受信時刻と前の受信情報の認証、再配信・再起動、途中の入力、3種類のprovider、公開イベントと表示用の本文を確認した。既存の圧縮forkの検証にも時刻付き入力を使い、親の送信文脈がそのまま引き継がれることを照合する。時刻情報を表示できることを、モデルがあらゆる時間関係を正しく解釈する証明にはしない。

検証中、制御応答を待つ間に保存処理へ再入する経路で、既定のテスト用スタックが尽きることが分かった。デバッガで大きな終端保存のfutureに絞り、その処理だけをヒープへ移した。入力の処理順序は変えず、生成中の各文字更新に大きな割り当てを追加する形も避けた。問題が出たkill／restartと混雑時の制御ケースは、スタック上限を引き上げずに通過した。

読みやすい表示へ修正する前の実装 `97e3062e` の専用実行環境では、実際のAPI・PersonalityAgent・GLM-5.3 Flashに合成メッセージを2通送った。初回は前回の受信情報がnullであること、2通目の前回時刻と番号が初回のものと一致することを確認した。モデルは2通目の受信時刻 `2026-09-08T03:10:10.017541347Z`、前回の番号 `1`、差 `16926.026803` msを正しく返した。公開イベントの原文も送信した文字列と一致し、116フレームを予期しない切断なく受信した。これは時刻情報の可視性と受け渡しの確認であり、読みやすさの確認ではない。ユーザーの指摘を受け、この生のms表示は上記の秒・分・時間表現へ修正した。モデルが時間関係を常に正しく解釈する証明でもない。

表示修正後の `9d0988e0` でも新しい専用環境へ2通送信した。モデルは初回に受信時刻だけ、2通目に `[Received 2026-09-08 03:29:04 UTC; approximately 10 seconds since the previous incoming message]` を返した。保存された受信間隔は約9.929秒で、表示の丸めと一致する。原文の保持、前回の受信情報、92フレームの受信と通常終了を確認した。修正後の3種類のprovider送信・圧縮fork・見積もり・実ドライバを含む関連7テストも通過した。

## 参照したハーネス

Codexの公開実装には、featureで有効になる `current_time_reminder` があり、モデルへ現在のUTC時刻を追加する。これは受信イベントごとの受信時刻・間隔とは異なる。[公開コード](https://github.com/openai/codex/blob/main/codex-rs/core/src/session/time_reminder.rs)

Claude Codeの公式 `UserPromptSubmit` フックは、提出された入力に追加コンテキストを渡せる。フックで時刻情報を構成する余地はあるが、標準で各入力に時刻や間隔を添える機能までは確認していない。ログにある時刻を、モデルも見ているとは扱わない。[公式Hooks文書](https://code.claude.com/docs/en/hooks)
