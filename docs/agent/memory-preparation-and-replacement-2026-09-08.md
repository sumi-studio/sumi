# 記憶整理の準備と差し替えを分ける

2026-09-08。[最初の実装と実行確認](memory-context-implementation-2026-09-08.md)に対する、ユーザーの追加指定を反映する。

## 準備する時期

通常のL0チャンクは内部推定10,000トークン以上で、次の通常のユーザー入力の直前の安全な境界で区切る。ツール呼び出しと結果、その直後の応答を途中で切らない。大きなチャンクの退避用の境界は従来の2倍という関係を保ち、20,000を超えた場合に評価する。

区切られた範囲について、次の実際の親のモデル呼び出しと同じ文脈・モデル・設定から、非同期にL1候補を作る。整理分岐は同時に1件。完成した候補は保存して待機させる。完成したという理由だけで、通常の文脈へ挿入したり、対応するL0やprovider固有の継続情報を取り除いたりしない。

これは定時の振り返りや、本人が整理したいと判断して始める行為を実装したものではない。容量管理に伴う準備の時期を基盤が決め、整理内容を同じ文脈のモデルに任せる仕組みである。

## 差し替える時期

生きているL0全体の内部推定が40,000を超えたときに、準備済みのL1への差し替えを認める。40,000ちょうどでは差し替えない。推定には通常の記録の見積もりとprovider固有の追加量、保存された補正値を使う。APIの実請求トークンと同じ値だとは扱わない。

会話処理が待機状態にあり、現在の文脈を更新できるところで、完成済みの古いチャンクから必要な分だけ差し替え、L0が40,000以下になったら止める。30,000まで減らすことを別の必須条件にはしない。まだ整理が終わっていない古いチャンクがあっても、ほかの完成済みチャンクを適用できる。完成した候補がなければ原文を維持し、会話を待たせない。

候補の完成時点では40,000以下だった場合でも、その後の会話で閾値を超えたら、既に準備してある結果を適用できる。新しい整理分岐の完成通知を必須にしない。再起動後も、準備済み候補と現在の量から同じ判断を行う。

差し替えでは対象の版を照合し、整理後に届いた入力を上書きしない。原文そのものは保存する。`KEEP_UNCHANGED` は原文維持の判断であり、量を減らすためだけにその判断を覆さない。

意図は、L1候補を先に用意しておき、必要になるまで親の文脈を保つことで、準備の待ち時間と不要な文脈変更を減らすこと。実際のキャッシュヒット率や費用改善は、この条件変更だけから保証しない。

実際にproviderが文脈上限を返した場合の、一時的な送信範囲の制限は別に扱う。その制限は同じ記憶の再読み込みや新着だけでは解除しないが、永続的なL0→L1の置換が反映されたら、古い記憶構成に対して計算した制限を解除する。これにより、整理後も以前の狭い予算だけを理由に原文を外し続けることを防ぐ。新しい構成も上限を超える場合は、既存の回数制限付き復旧で改めて送信範囲を計算する。原文の削除やL1→L2の自動生成を行う処理ではない。

## 文脈を知っている範囲と、書き換える範囲

整理分岐には親と同じ文脈を渡す。後続の出来事を隠すことで混入を防ぐ設計にはしない。一方、L0→L1の出力は指定部分をその位置で置き換える文章であり、前後の文脈は対象を読み解くために使う。他のチャンクの出来事を取り込まず、後から知った事実で当時の理解を書き換えないよう、整理プロンプトに短く境界を示す。

例えば対象内で「赤だ」と考え、後のチャンクで「青だった」と訂正した場合、前の対象だけを「青だった」に直すと理解の変化が失われる。双方を含む範囲を統合するときには、その変化を結び付けられる。この指示で意味の混入を完全に防げるとは扱わず、実際の出力で確かめる必要がある。

適用済みのL1は、元のL0チャンクがあった位置に置く。例えば古いAを原文のまま保持し、Bだけ整理済み、Cは新しい原文なら、送信する順番もA→Bの置換文→Cとなる。すべてのL1を会話の先頭へ集める方式は廃止する。順序は元のL0の保存順で決め、時刻や整理の完成順、L1側で採番された順序では決めない。

置換文は受信メッセージを装わない内部の文脈として挿入し、元の保存IDや受信時刻を捏造しない。ツール呼び出しと結果を含むチャンクを途中で分割しない。親の文脈を確定する前に配置するため、整理分岐も同じ順序を引き継ぐ。provider自身の不透明な圧縮領域が有効な場合、その内部を並べ替えたとは扱わない。

実際の組み立て処理からHTTP送信までの検証では、Responsesの独立した推論項目が公開のThinking項目を伴わないと除外される既存の問題も見つかった。Responsesでは同じ出力位置に両者を置けないため、対応する永続メッセージ・provider・モデル・出力位置を確認したうえで推論項目を保持する。Anthropicの署名付きThinkingの扱いは同じ条件へ一律変更しない。

2026-09-09時点では、runtimeにL1→L2とL2内部の再統合も接続されている。L1→L2は指定されたL1の範囲をその位置で置き換え、L2内部では指定された既存L2の中に限り構成を組み直せる。対象外のL0やL1の出来事を持ち込むことは認めない。操作ごとにプロンプトを分け、対象の版と元の履歴への対応を保つ。以前この文書にあった「L0→L1のみ」「上位整理は未接続」という記述は、後続の実装により古くなった。

L1・L2の閾値は整理を始める条件であり、容量を必ずその値以下にできる保証ではない。`KEEP_UNCHANGED`、縮まない結果、失敗の場合は原文を維持する。段階的な実モデル検証とその限界は[受け入れ記録](foundation-completion-2026-09-08.md)に記載している。継続的な圧力下の回復と意味の保持は、その一回の成功だけで確認済みとは扱わない。

## Agent Experience：想起と履歴参照を混同させない

旧名 `memory_recall` は、エージェントにも「自分の記憶を想起する操作」と受け取れる名前だった。実際の機能は保存された会話とツール記録の検索・取得なので、公開名を `conversation_history` に改め、説明、結果のscope、通常の指示、整理結果からの参照案内を揃える。旧名の互換経路は追加しない。

この道具の利用は、保存された記録を開いて読むこととして提示する。モデル内部で思い出すことを実装した、という意味を持たせない。誰の記録を読めるか、原文の認証、長い記録のページング、画像の取得は変更しない。利用するかどうかは本人に委ね、メモや振り返りの義務を加えない。

以前の実行記録にある `memory_recall` は、その実行時点の実際の名前であり、後から書き換えない。
