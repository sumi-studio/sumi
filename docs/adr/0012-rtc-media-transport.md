# ADR 0012: 通話（RTC）のメディア配信方式

- Status: Proposed
- Date: 2026-08-05
- Related:
  - [ADR 0011](0011-messaging-surface-and-agent-participation.md)
  - [メッセージング接続契約（凍結 v1）](../messaging-boundary-contract.md)

## コンテキスト

メッセージングに音声・ビデオ通話を足す。DM・グループ DM・ボイスチャンネルの
三つの文脈で「今この場所で誰が話しているか」が見え、参加・退出・ミュート・
カメラ・画面共有ができ、通話中もそのままテキストで会話が続けられること。

要件は次の五つで、順序がそのまま優先度である。

1. **参加人数**: 1 対 1 だけでなく、チャンネル単位の 10 人前後の通話が成立する
   こと。組織は 1000 人規模を想定するが、同時に一つの部屋へ入るのは
   room（= place）単位なので、必要なのは「一部屋あたりの人数」である。
2. **録音**: 後日、通話の録音・書き起こしを行いたい（人格 agent が場に
   参加していくうえで、音声だけが記録に残らない層になるのは困る）。今すぐでは
   ない。
3. **通話品質**: 回線の弱い参加者が一人いても、他の参加者の品質が巻き添えで
   落ちないこと。
4. **運用コスト**: pre-launch であり、専任の SRE はいない。運用対象が増えるほど
   壊れる。
5. **プライバシー / データ主権**: 会話内容は Sumi が置いた場所に留まること。
   第三者 SaaS のサーバーを音声が素通りする構成は、テキストを自前で持っている
   今の設計と釣り合わない。

## 検討した選択肢

| 方式 | 参加人数 | 録音 | 品質 | 運用コスト | データ主権 |
| --- | --- | --- | --- | --- | --- |
| **mesh P2P（WebRTC 直結）** | 3〜4 人で頭打ち。各人が N-1 本を上り送信する | 各クライアントで録るしかなく、欠落する | 上りが弱い一人が全体を巻き込む | サーバーはシグナリングのみで最小 | 完全に自前 |
| **self-hosted SFU: LiveKit** | 部屋あたり数十人。simulcast で受信側ごとに層を選ぶ | egress を後から足せる（サーバー側で録れる） | simulcast + 帯域推定が内蔵 | 単一バイナリ 1 サービス。設定は API key/secret とポートのみ | 完全に自前 |
| **self-hosted SFU: mediasoup / Janus** | LiveKit と同等 | 自前で書く | 同等 | ライブラリであってサーバーではない。シグナリング・部屋・権限・再接続をすべて自作する | 完全に自前 |
| **マネージド SaaS（Twilio / Agora 等）** | 十分 | 提供される | 良い | 最小 | 音声が第三者を経由する。従量課金が読めない |

## 決定

**self-hosted LiveKit（SFU）を軸に据える。**

- OSS（Apache-2.0）で、単一バイナリ 1 サービスとして立つ。SFU・simulcast・
  画面共有・再接続がサーバー側に内蔵されており、mediasoup / Janus のように
  部屋と権限とシグナリングを自作する必要がない（要件 4）。
- SFU なので送信は 1 本、受信側ごとの層選択は SFU が行う。弱い回線の一人が
  他の参加者の上りを巻き込まない（要件 1・3）。mesh P2P はここで落ちる。
- 録音は egress を後から別プロセスとして足せる。今は入れない（要件 2）。
- 自分たちのネットワークに置くので、音声・映像は Sumi の外へ出ない（要件 5）。
- 部屋は place 単位である。組織が 1000 人でも、同時に同じ room へ入るのは
  その place のメンバーだけなので、SFU 1 台 + 将来の room 単位の水平分割で足りる
  見込み。room を跨いだ状態共有を作らないことをこの ADR の制約とする。

### 境界の置き方

- **サーバー（`apps/api`）は「誰がどの部屋に入ってよいか」だけを決める。**
  place のメンバーであることを既存の Store の権限モデルで確認し、
  room = place_id・identity = participant key のアクセストークンを発行する。
  メディアは API を通らない。
- **通話状態（誰が今その place で通話しているか）の正本は LiveKit ではなく
  api のメモリに置き、WS イベント `call_state` で配る。** LiveKit の webhook
  （`participant_joined` / `participant_left` / `room_started` / `room_finished`）
  を受けて更新する。プロセス再起動後の最初の `GET /messaging/calls` では LiveKit
  RoomService の `ListRooms` / `ListParticipants` から投影を復元してから現在値を返す。
  テキストのように durable な seq を持たせない。
- **identity は participant key（`human:<id>` / `personality_agent:<id>`）。**
  人間と人格 agent を通話でも同じ「参加者」として扱い、bot 用の別枠を作らない。

### アクセストークンを自前で発行する

`github.com/livekit/protocol/auth` は使わない。**JWT を標準ライブラリで組み立てる。**

理由: `livekit/protocol` を入れると、この API が共有している grpc・protobuf・
otel・`golang.org/x/*` の版が軒並み引き上げられる（実測で 20 以上のモジュールが
upgrade / added になる）。UI/UX の変更に依存グラフ全体の更新を同梱するのは、
壊れたときに原因を切り分けられなくする。LiveKit のアクセストークンは HS256 の
JWT に `video` grant を載せただけの、公開され安定した形式であり、
`crypto/hmac` + `encoding/json` で 60 行に収まる。webhook の検証も同じ鍵の
JWT と本文の SHA-256 の照合だけである。

将来 egress・room 管理 API・SIP など server SDK を本当に必要とする機能を入れる
段になったら、そのときに依存として迎える。

### 今はやらないこと

- **E2EE**。LiveKit は insertable streams による E2EE を提供するが、鍵配布の
  設計（誰が鍵を持ち、後から参加した人にどう渡し、録音とどう両立するか）は
  この ADR の範囲を超える。**現時点で通話は SFU で復号可能であり、E2EE では
  ない**ことを要件表に明記して先送りする。
- **録音・書き起こし**。egress を足す形で後日。
- **agent の通話参加（音声合成での発話・音声認識での聴取）**。人格 agent は
  `get_call_state` で「今どの place で誰が通話しているか」を読めるが、通話へ
  入る道具は作らない。人間と同型に扱うなら agent も通話に入れるべきだが、
  それは音声合成・割り込みの作法・発話権といった別種の設計判断を要求する。
  読めるだけにして、書けないことを明示的な将来課題とする。
- **通話の永続的な履歴**。「通話がありました」というメッセージを timeline へ
  残すかは、録音を入れる段でまとめて決める。

## 結果

- 新しい運用対象が 1 つ増える（livekit-server）。ローカルでは compose に
  1 サービス、本番では 1 コンテナ。UDP を通す必要があるため、ローカルは
  rtc-mux（単一 UDP ポート）で公開する。
- **鍵はリポジトリに置かない。通話は両側とも opt-in である。**
  `SUMI_LIVEKIT_API_KEY` と `SUMI_LIVEKIT_API_SECRET` の両方が設定されたとき
  だけ、api は通話 route を生やし、launcher は compose の `calls` profile を
  有効にして livekit-server を起動する。どちらも未設定なら通話は無効で、
  メディアサーバーは**そもそも起動しない**。片方だけの設定は設定誤りとして
  起動前に失敗させる（資格情報を失った後も `down` は動く）。既定の鍵を
  リポジトリに書くと、無設定の stack が「公開された鍵で誰でも room token を
  署名できるメディアサーバー」を晒しながら api 側の通話だけが無効、という
  最悪の組み合わせになる。
- `apps/api` の Go 依存は増えない。
- `apps/web` は `livekit-client` を 1 つ追加する。UI コンポーネント
  ライブラリ（`@livekit/components-react`）は使わない — 通話 UI は既存の
  デザイントークンの上に自前で書く方が、見た目の一貫性を保てるうえに
  依存も薄い。
- LiveKit が動いていない環境でも、通話ボタンが失敗するだけでメッセージングは
  そのまま動く。通話は追加の層であって、テキストの前提ではない。
